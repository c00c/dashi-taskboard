Why the two deferrals are deferrals

Both were accepted as real. Neither was fixed, and the reason is recorded rather than left implicit.

Cloud mode hides synced work

The cloud worker contains no external-work references at all, and the cloud D1 migrations define no external_origin / external_id columns — the local schema does. Cloud has never been able to store external work identity, so this is a pre-existing structural gap that the branch made quiet rather than a capability it removed. Closing it needs new cloud migrations and worker routes; the settled spec puts cloud-hosted deployment out of scope. Carried as a known limitation.

Harness demo page in the repo

The reviewer is right on principle. The Agent Loop work order mandates this exact code-stamped path for the round’s preview, so removing it would break the stage contract. Raised for the harness, not actionable inside this change.

Fix lanes

Split by conflict domain, not by finding count, so no two workers touched the same file. Workers wrote only in their own worktree; integration onto the canonical branch happened once, here.

Pass 2 — the fixes that were only half-applied

Both reviews ran again against the integrated pass 1 branch. Three findings came back, all verified against source, all fixed. Two of the three were pass 1’s own corrections applied to TaskDetail.tsx and TaskEditor.tsx but never to the third site, TaskCard.tsx — which is the case for running a second pass rather than trusting the first.

medium Board-card quick edits bypassed the provider write set. TaskCard rendered priority, label and due-date controls with no capability check at all, so an Azure DevOps card dispatched mutations the server rejects with 409. medium The write set went stale across a source change. TaskDetail’s effect was keyed on [task.source] but never cleared the previous provider’s capabilities, so a task could be judged against the prior provider until the fetch landed. Fixed by deletion: the effect and its state are gone and the write set is derived at render time. S fixed

The hard-coded === "jira" assignee guard had been returning the right answer by coincidence. Jira declares priority, labels and due date but not assignee; Azure DevOps declares assignee but none of the other three. The two providers are near-inverses, so a guard naming one of them happened to be correct for that one and silently wrong for the other. Deriving from declared capabilities makes both correct by construction — which is what ticket 04’s provider-neutral seam asked for.

How pass 2 sourced the capability list

TaskCard renders once per card, so the obvious fix — fetch the provider list inside the card — would have cost one HTTP request per card on the board.

One fetch, existing path

The list is fetched once in App and drilled through BoardColumn and OtherTasksPanel along the exact prop path availableLabels already uses. No new cache, no new mechanism.

web/src/App.tsx +15 lines

Derived, not stored

Each card computes its own write set from its own task.source at render time. A card can no longer be judged against another provider’s rules, because nothing is held in state to go stale.

web/src/components/TaskDetail.tsx −15 lines

Unknown stays editable

Before the fetch resolves — or if it fails — the list is empty, the write set is null, and every field stays editable with the server’s 409 as the backstop. A transient failure cannot lock the board.

web/src/externalWriteSet.ts unchanged

Reported rather than hidden: the staleness in finding 3 is real at the component level but hard to reach in the running app, because TaskDetail is rendered with key={detailTask.id} and remounts when the task changes. It was still fixed — the fix is a net deletion, and it removes the trap if that key is ever dropped.
